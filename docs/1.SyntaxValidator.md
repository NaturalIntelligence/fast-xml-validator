# SyntaxValidator

`SyntaxValidator` checks that an XML document is **well-formed**. It does not
validate against a schema or business rules — for that, see
`BusinessRulesValidator`.

```js
import { SyntaxValidator } from 'fast-xml-validator';

// static, one-shot (same as v1)
SyntaxValidator.validate('<root/>');                 // -> true
SyntaxValidator.validate('<root>', {});               // -> throws ValidationError

// instance form (new) — reuse the same configured validator for many documents
const validator = new SyntaxValidator({ multipleRoots: true });
validator.validate('<a/><b/>');                        // -> true
```

Both forms throw a `ValidationError` (`{ message, code, line, col }`) on the
first problem found; they never return a `{ err }` object — `validate()`
either returns `true` or throws.

## Always-on validations

These run unconditionally — they cannot be turned off, since they represent genuinely non-well-formed XML:

- **Illegal control characters** — `0x00–0x08`, `0x0B`, `0x0C`, `0x0E–0x1F` are rejected wherever they appear literally: element text, attribute values, and comment bodies. (Tab/LF/CR remain legal whitespace.)
- **Unquoted attribute values** — `attr=value` or `attr=` without a quoted value now consistently errors (this already partially worked in v1 via a generic "is without value" message; v2 makes it a first-class, intentional check performed by `AttributeStringValidator`).
- **Multiple / misplaced `DOCTYPE`** — a second `<!DOCTYPE ...>` anywhere in the document, or any `<!DOCTYPE ...>` that appears after the root element has started (i.e. not at the very top of the document), is rejected.

## Config-driven validations

All default to `false` / off.

```js
SyntaxValidator.validate(xmlData, {
  invalidCharSequence: {
    comment: true,   // '--' inside a comment body (besides the pair before '-->')
    tagValue: true,  // ']]>' inside element text content
    attrLt: true,    // '<' inside an attribute value
  },
});
```

| Option | Meaning |
| --- | --- |
| `invalidCharSequence.comment` | Reject `--` anywhere inside a comment's body. |
| `invalidCharSequence.tagValue` | Reject `]]>` inside element text content. |
| `invalidCharSequence.attrLt` | Reject a literal `<` inside an attribute value. |

## XML declaration handling

```js
SyntaxValidator.validate(xmlData, {
  xmlDeclaraion: {   // (also accepts the correctly-spelled `xmlDeclaration`)
    optional: true,     // default: declaration is optional
    argPosition: true,  // default: version/encoding/standalone must be in order
  },
});
```

- `optional: false` — the document **must** start with `<?xml ... ?>`;
  omitting it is an error.
- `argPosition: true` (default) — `version`, `encoding`, and `standalone`
  must appear in that order when present (this matches the v1 behaviour,
  which always enforced order). Set `argPosition: false` to accept any order
  of the three attributes.

## Multiple root elements

```js
SyntaxValidator.validate('<a/><b/>', { multipleRoots: true }); // -> true
```

By default (`multipleRoots: false`) a document must have exactly one root
element, as required by the XML spec. Setting `multipleRoots: true` relaxes
this — conceptually, every top-level element is treated as a child of an
implicit **virtual root**, so any number of sibling top-level elements is
accepted, while stray top-level text is still rejected (a virtual root can
have element children, not text).

## Skipping tags from validation

```js
SyntaxValidator.validate(xmlData, {
  skipTags: ['..script', '..style', 'root.rawData'],
});
```

`skipTags` accepts [`path-expression-matcher`](https://www.npmjs.com/package/path-expression-matcher)
expressions (the same syntax used by `fast-xml-parser`'s `stopNodes`), e.g.:

- `"..script"` — any `<script>` anywhere in the document
- `"root.rawData"` — `<rawData>` directly under the root
- `"row[type=raw]"` — a `<row>` with `type="raw"`

Once a tag's path matches one of these expressions, its **entire subtree**
(attributes, text, nested tags — everything up to and including its own
closing tag) is treated as opaque raw content, the same way CDATA is:
**no validation is performed on it at all**, including the always-on control
character or unquoted-attribute checks. This is useful for embedding
non-XML payloads (script bodies, legacy markup fragments, etc.) inside an
otherwise well-formed document.

Matching is a literal search for the first `</tagName>` (optional whitespace
before `>`) after the opening tag — mirroring how `<![CDATA[ ]]>` content is
found. This means same-named tags inside a skipped subtree do **not** nest;
the first closing tag of that name ends the skip. This matches the common
`<script>`/`<style>` use case. If your skipped content can itself contain a
literal `</tagName>` substring, scope the skip expression more narrowly.

## Options reference

| Option | Type | Default | 
| --- | --- | --- | 
| `allowBooleanAttributes` | `boolean` | `false` |
| `unpairedTags` | `string[]` | `[]` |
| `docType.maxEntityCount` | `number` | `Infinity` |
| `docType.maxEntitySize` | `number` | `Infinity` |
| `invalidCharSequence.comment` | `boolean` | `false` |
| `invalidCharSequence.tagValue` | `boolean` | `false` |
| `invalidCharSequence.attrLt` | `boolean` | `false` |
| `xmlDeclaraion.optional` | `boolean` | `true` |
| `xmlDeclaraion.argPosition` | `boolean` | `true` |
| `multipleRoots` | `boolean` | `false` |
| `skipTags` | `string[]` | `[]` |
